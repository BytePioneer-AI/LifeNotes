10 天 AI 协作开发实录：一份可复用的 AI 开发流程样例

想先看效果？点击查看演示页面：演示页面

我用 10 天时间，借助多个 AI 模型和工具，完成一个项目的需求分析、产品设计、架构设计、数据库设计以及前后端开发。

这是一份可复用的 AI 辅助编程参考样例。过程中使用了不同模型与工具的优势能力。核心理念是以人为本：以自己的核心思路为基础，让模型帮你扩展成完整、具体、可落地的产品文档。核心思路一定是人的，模型只是用于激发与拓展人的思路。

模型/工具 阶段
Gemini 3Pro 网页版 需求分析、产品设计、架构设计、数据库设计
Gemini 3Pro / Antigravity 产品原型/UI 设计
GPT5.1 / Codex 代码审核：后端开发、前端开发
Claude 4.5 / Kiro 代码编写：后端开发、前端开发
GLM 4.6 / Claude Code 简单问题梳理

0. 概览

工具与模型定位

开始前，我先简要说明为什么会用到这些模型和工具。

Gemini 2.5 和 Gemini 3 都很擅长逻辑判断与事件分析。8 月份我发布过用 Gemini 2.5 辅助产品设计的博文：《一种通过结构化提问，与LLM共创高质量PRD核心的实用指南》。这个模型的价值在于处理项目中的“设计”类工作，往往比 GPT、Claude 更出色。而 Gemini 3 的前端设计能力尤其强，也适合做 UI 设计。

Antigravity 是 Google 新推出的 AI-IDE，有免费额度，但门槛较高(主要是容易封号)，主要用于生产 HTML 的 UI 原型图。如果没有 Antigravity，用网页版也可以。

Codex 是 OpenAI 的 AI 编程工具（CLI 命令行/插件）。它比 Claude Code 更严谨、更可信，我把它当成一把精准的外科手术刀，用于代码审核，尤其适合审查其他模型写出的代码。审核的意义在于：我用 AI 越多，越意识到 AI 的不可靠，尤其在复杂逻辑上更明显。所以需要 Codex 根据最初需求与最终代码，检查是否符合业务需求以及代码本身是否存在问题。新版本 5.2-Codex 在指令遵循方面表现非常严格，适合解决疑难 Bug，而不太适合大型项目的奠基阶段。

Kiro 是亚马逊推出的 AI-IDE。推荐原因可见：https://mp.weixin.qq.com/s/Js9Pvclobge8dd168zSY4Q。`Kiro` 提出了 Spec 模式，即将一次代码工作拆分为：需求文档 -> 设计文档 -> 任务文档。每个流程都可人工干预。除 Kiro 外，还有两个开源的 Spec 项目，适用于多个 AI 工具（如 Codex、Claude Code 等）：1) Spec-kit：适合新项目，从 0 到 1 构建；2) Open-Spec：更轻量，适合旧项目新增功能，我更推荐这个。Kiro 目前仅支持 Claude 模型，且价格性价比很高。

GLM 4.6 / Claude Code：简单说，就是“国内的人开外国的车”。GLM 4.6 是智谱开源模型，性能约等于 Claude 4.1，但价格低，官方还有 20 元包月的编程套餐。Claude Code 是 Anthropic 发布的 AI 编程工具（CLI 命令行/插件），功能强大。总体来说 GLM 能力略弱，尤其在长上下文时性能下降明显，但在不想消耗 Codex、Kiro 额度时，GLM 的性价比很高。

这个博主对几个模型的总结也不错，可参考：https://mp.weixin.qq.com/s/PmOxyaY3QUZe59Ya5hjl7A

核心思路

先用一句话概括全流程：用 Gemini 3 产出需求与设计文档作为“地基”，再以 Spec 驱动后端与前端开发，由 Codex 贯穿代码审查与纠偏，最终将文档与实现闭环对齐。

  A[需求与产品设计
Gemini 3] --> B[原型与 UI 设计]
  B --> C[架构与数据库设计]
  C --> D[后端开发

  D --> E[前端开发]
  E --> F[持续审查与纠偏

  F --> G[交付与迭代]

需求与文档产出

利用 Gemini 3 完成产品设计，输出一份完整的需求文档。

再基于需求文档，并善用 Google AI Studio 的分支能力，用 Gemini 3 完成原型设计、UI 设计、数据库设计与后端架构设计，最终沉淀为《需求文档》、《数据库设计文档》、《开发技术规范清单》、《后端架构设计文档》、《后端开发步骤清单》。

后端开发流程

根据 Spec 理念驱动开发，依赖需求文档、数据库设计文档、后端架构设计文档与后端开发步骤文档，使用 Claude 分阶段实现。

开发过程中，使用 Codex 对照文档逐条审查 Claude 的代码并修正。

如此循环，逐步完成后端开发步骤文档的每个阶段。

前端开发流程

基于 Gemini 3 生成的 UI HTML 页面进行前端 React 开发。使用 Codex，因为它的指令跟随能力更强，能更好还原 UI 设计图的样式；而 Claude 容易发散、Gemini 3 的工程化能力偏弱（经常出现修改文件导致错误）。因此我们组合了 Gemini 3 的前端设计能力与 Codex 的工程能力与指令跟随能力。

前端这部分主要是设计一个解耦清晰的组件结构，逐个接入后端接口，发现小问题再不断优化。

前端组件与样式

  1. 已有组件：用 Codex 将 React 代码转为 HTML + TailwindCSS，再交给 Gemini 3 基于现有代码给出多个样式方案。确定方案后，让 Codex 生成/修改 React 代码。
  2. 没有组件：将需求交给 Gemini 3 生成多个方案，后续流程同 1。

Google AI Studio 分支协作

我把初始需求对话作为“主线”，在 Google AI Studio 里复制上下文后开出 5 个分支窗口。每个分支都继承完整背景，因此在做专项设计时不会丢失需求信息。

这 5 个分支分别负责 UI 设计、数据库设计、总体架构设计、后端架构设计等不同方向，相当于 5 位“虚拟专家”。有具体问题时，我直接进入对应分支进行沟通解决。

1. 需求分析与产品设计

首先要有一个核心功能需求，不需要完整，只需几句话。然后让 Gemini 辅助我们激活思维、逐步补全需求。Gemini 会提供思路与选项，但人要保持清醒：不要完全依赖 AI，核心思路必须来自人。

如何利用 Gemini 帮我们设计产品？可以查看我之前的文章：《一种通过结构化提问，与LLM共创高质量PRD核心的实用指南》

  2. 人：因为上一次回答一般，所以我提供一个大致思路引导 LLM。
  1. 经过几轮对话，确定了核心页面结构

  1. 又经过几轮对话，基本敲定产品主要功能与核心交互方式。产品设计虽然是由 Gemini 引导流程，但在具体需求与设计上，一定是“人”来主导。LLM 往往提供好坏参半的思路，我们必须能清晰识别并修正。

1.2 《需求文档》

最终产出：一份包含产品定义、背景、目标用户、功能需求与基本交互方案的需求文档。这份文档很重要，后续的 UI 设计、后端架构设计、前端页面实现都需要它作为基础。

关键产出要点

  1. 明确目标用户与核心场景，完成需求边界收敛。
  2. 固化核心功能与交互原则（AI 预处理 + 人工复核）。
  3. 形成可复用的《需求文档》，作为后续设计与开发基准。

2. 产品原型

基于上一轮得到的“核心功能” + “核心页面结构”，可以让 Gemini 使用 ASCII UI 绘图法 画出线框图。

线框图的优点：

  1. 更聚焦当前工作：让大模型暂时不关注交互方式，核心聚焦页面结构。
  2. 更容易修改：大模型产出的原型通常需要多次修改，ASCII UI 绘图法比 HTML 的迭代速度更快。

  3. 为后续 UI 设计提供结构化蓝本。

4. Google AI Studio 分支协作

在 Google AI Studio 中，可以基于当前对话历史新开分支窗口。这样新窗口会保留与 Gemini 的需求沟通记录，后续做其他设计时能更准确理解需求。我以最初的需求对话为基底，分支了 5 个窗口，分别处理 UI 设计、数据库设计、总体架构设计和后端架构设计。

这 5 个分支相当于我的 5 个专属开发专家，有问题就到对应窗口沟通即可。

如果没有这个分支能力，用我们最核心的 “需求文档” 作为对话基础也可以。

关键产出要点

  1. 用分支并行解决专项设计，避免上下文丢失。
  2. 每个分支沉淀独立结论，提高协作与复用效率。
  3. 形成“主线需求 + 专家分支”的协作范式。

  3. 降低跨模型协作时的信息偏差。

10. Spec 驱动开发

在 Kiro 的 spec 系统中，这三个文档各有明确的职责和含义：

  1. requirements.md - 需求规范
    定义“做什么”和“如何验证”。描述功能需求、用户故事（Why）与验收标准（How to verify），作为测试与验收依据。
    例：需求写明“配置从环境变量加载”，验收标准写明“缺失变量时报错”。

  2. design.md - 设计文档
    定义“怎么实现”和“为何这样设计”。给出技术方案与架构，说明关键决策与正确性属性，并覆盖错误处理、测试与部署考虑。

  3. tasks.md - 实现计划
    定义“怎么做”和“进度如何跟踪”。把设计拆成可执行任务，标注需求追溯与完成状态，用于项目管理。

总结

工作是你的，不是工具的。AI 会让开发者失业吗？不会，但前提是你愿意进化。工具一直在变，从打孔器到编译器，从单机到微服务，每一代人都有焦虑，但建设者从未消失。AI 生成代码很快，但看懂它、判断它、为它负责的始终是你。
